English Mastery v1.0.2 Hotfix 11 - Final Validation Report
Date: 2026-09-01

PURPOSE
Fix persistent Today Mission load failures by exposing exact backend diagnostics and adding safe degradation; expand Tenant Admin Word Books for incremental management; and add configurable Task Queue execution timeout with delete/retrigger lifecycle. Default task timeout is 120 minutes.

IMPLEMENTED
1. Today Mission reliability / diagnostics
   - `/api/student/plan` returns a structured `student_plan_failed` error with code, exact stage, backend message and requestId.
   - `X-Request-Id` is emitted and the same ID is written to server logs.
   - Student Today and Learning Momentum display the concrete backend diagnostic instead of only “Refresh to try again”.
   - Planner/policy/materialisation failures degrade to an emergency Today mission when core `learning_tasks` storage remains usable.
   - Completion reconciliation and streak are best-effort and cannot block an otherwise valid Today mission.
   - Progress Calendar uses the same code/message/stage/requestId diagnostic model.

2. Tenant Admin Word Books inventory
   - Existing Tenant and System word books are listed with term counts and stage metadata.
   - Tenant books support View/Search terms, rename, description/stage editing, Add terms through the persistent background import queue, individual-term removal and protected deletion.
   - System books are visible for reference and are read-only.
   - Fixed the actual content-list SQL ordering field to `v.lemma`; a full migrated SQLite database executes the query successfully.

3. Configurable Task Queue timeout
   - Migration 0051 adds `queue_runtime_policy`.
   - Default timeout is 120 minutes; supported range is 5–1440 minutes.
   - Tenant Admin and Platform Work Queue APIs/UI read and save the timeout.
   - The Task Runner watchdog checks stale running tasks every 5 minutes.
   - A task exceeding the configured execution timeout becomes terminal `failed / timed_out` and records `job_timed_out` diagnostics.
   - Timed-out queue history can be deleted or retriggered.
   - Retrigger creates a fresh queued execution and preserves the original timed-out task/logs for audit.
   - Queue remains strictly single-consumer: max_batch_size=1, max_concurrency=1, oldest persisted enqueued_at first.
